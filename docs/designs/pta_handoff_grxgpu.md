## A. MSI vectors and command queue — baseline §8 items 3–4

The PTA exposes `PTA_IRQ_STATUS` causes (`CAL_DONE`, `ERR`, `DRIFT_ALARM`, `SAT_THRESHOLD`) and `PTA_IRQ_MASK`; the regmap specifies a message-signaled interrupt through the GPU's CXL.io function. This handoff recommends MSI-X for the function. The GPU dispatcher also needs a defined chiplet queue contract.

1. **MSI-X capacity and allocation — recommended baseline:** Use a two-entry MSI-X table on the GPU's CXL.io function. Vector 0 is reserved for GPU/CP command completion once the CP interrupt is wired to a host ISR; vector 1 is an aggregate PTA interrupt for `CAL_DONE`, `ERR`, `DRIFT_ALARM`, and `SAT_THRESHOLD`. The existing CP `irq` pulse is not currently wired to a host ISR, so vector 0 is a recommended allocation, not a claim of working completion interrupts today. The handler reads `PTA_IRQ_STATUS` to identify the cause; `PTA_IRQ_MASK` and RW1C status semantics remain authoritative. This is one vector for the current CP completion stream and one for PTA, not one vector per PCIe request. To determine actual function capacity, inspect the endpoint's MSI-X capability in PCI configuration space: its Table Size field is encoded as the number of entries minus one, so a field value of 1 represents two entries. Separately record the number the OS/driver actually allocates; that can be less than the table capacity. Confirm that the selected PCIe/CXL function IP exposes two entries and that the driver obtains two. If either check yields fewer than two, report the limitation and get an explicit fallback decision rather than silently changing the mapping. Linux references: [`pci_msix_vec_count()`](https://github.com/torvalds/linux/blob/master/drivers/pci/msi/api.c), [MSI-X register definitions](https://github.com/torvalds/linux/blob/master/include/uapi/linux/pci_regs.h), and the [MSI Driver Guide](https://docs.kernel.org/PCI/msi-howto.html).
2. **Queue depth and active command:** What is the chiplet command-queue depth in commands, and does an actively executing command occupy a queue entry?
3. **Full-queue behavior:** What observable behavior occurs at capacity — backpressure, explicit rejection/error, or another defined response? Commands must not be silently lost.
4. **`PTA_STATUS.BUSY` meaning:** Does BUSY remain asserted while commands are queued, or only while one command executes? The completion contract depends on the GPU queue being empty and one `PTA_STATUS` read showing neither `BUSY` nor `CAL_BUSY`.

**Acceptance for questions 1–4:** Use the artifact checklist and closure table in the [GPU-owner evidence packet](../evidence/pta_gpu_owner_evidence_template.md). For question 1, keep the two-vector mapping as the owner-approved provisional driver/twin target, but pass only when the selected function/IP Table Size and actual host allocation are captured and the interrupt tests prove CP completion on vector 0 and each PTA cause on vector 1, including mask and RW1C behavior. If fewer than two are available, stop for an explicit fallback decision. For questions 2–4, keep closure blocked until the queue owners specify capacity/active accounting/full behavior/BUSY semantics and reproducible tests show no loss and no false completion.

The packet is a template, not evidence; every result remains BLOCKED until its referenced artifacts are attached and reviewed.

## B. UCIe posture and strategy-appendix alignment

5. **Confirm implementation of the normative posture and close register forwarding:** B4/L3 and [`board_icd.md`](board_icd.md) Link 2 record UCIe streaming in FLIT format with adapter CRC and retry; the GPU/board owner response has not yet supplied implementation confirmation or evidence. The prior strategy-appendix text recommending Streaming Raw Mode and describing control-only UCIe with optical bulk data conflicts with that baseline and is superseded by the corrected summary in [`chip_vs_board_strategy.md`](chip_vs_board_strategy.md). The exact GPU CXL.io BAR-to-EIC register-forwarding route is still open.

**Recorded design recommendation (not implementation proof):** Keep CRC-on FLIT + retry. UCIe mainband carries GPU-to-EIC tensor traffic; the optical segment is inside the EIC/PIC path. The PTA register window is planned as MMIO in the GPU CXL.io BAR, but the transport from GPU BAR decode across UCIe to the EIC register endpoint, including addresses, ordering, completion, and error propagation, must be specified by the GPU/EIC owners before the route can be considered closed. Do not assume sideband carries BAR transactions.

Any Raw Mode alternative remains non-normative unless B4/B7 are explicitly reopened and resolved by their owners, with register/control routing, integrity/recovery, and measured benefit documented. Do not claim corrupted digital operands are covered by the analog noise budget without supporting error-budget evidence.

**Acceptance for question 5:** GPU and EIC owners record confirmation or a named counter-proposal. Attach endpoint IP/configuration exports and link-training evidence for the selected FLIT + CRC/retry configuration, plus fault-injection evidence for CRC detection/retry and payload integrity. Attach the GPU BAR→bridge→UCIe transaction→EIC decode route and read/write/readback trace with ordering and error behavior. Keep Q5 **BLOCKED** until those artifacts are reviewed. The detailed artifact requirements and closure record are in the [GPU-owner evidence packet](../evidence/pta_gpu_owner_evidence_template.md).

## Disposition

The two-entry MSI-X mapping (vector 0 CP completion, vector 1 aggregate PTA) is owner-approved as a design decision and may be used as a **provisional target** for driver-contract prose and twin work. It is not verified behavior: function-IP Table Size and actual OS allocation remain unchecked, and fewer than two allocated vectors requires an explicit fallback decision. The twin must report only its implemented capabilities and behavior; it must not advertise recommended vectors, queue semantics, or link measurements as if verified.

Questions 2–4 (queue depth, active-command accounting, full behavior, and BUSY semantics) remain unanswered and block closure of the completion predicate and dispatcher queue sizing. Question 5 implementation confirmation and the GPU-to-EIC register-forwarding route remain open and block closing the EIC link/interface design. The checklist is an evidence plan, not a set of results; all boxes remain unchecked until owners attach artifacts. No MSI-X capability read, OS allocation record, interrupt-routing/waveform proof, or measured UCIe payload/RTT/credit evidence is recorded. The 57.6 GB/s and 100 ns values remain modeling assumptions. Further analysis does not close these items: the next closure input is the evidence packet filled with IP/configuration identifiers and reproducible artifacts, followed by owner disposition of each blocked item.

Driver/twin work that does not depend on the unresolved queue contract or measured link behavior may proceed against the provisional MSI-X mapping. Any behavior-dependent work remains gated, and the twin continues to report only what it actually implements.

## GPU-owner implementation sign-off checklist

**Project-owner disposition: APPROVED.** The user approved all recommendations below as project-level targets and evidence/acceptance criteria. This does not certify implementation, substitute for GPU/EIC technical-owner sign-off, or close any evidence gate. Use the [GPU-owner evidence packet template](../evidence/pta_gpu_owner_evidence_template.md) to record run identity, artifacts and hashes, and PASS/BLOCKED/FAIL dispositions; keep all boxes here unchecked until the evidence is reviewed.

- [ ] **PCIe/CXL function:** Record vendor/IP and configuration revision. Read the MSI-X capability from the function's PCI configuration space; record Table Size field and decoded entry count. Attach the IP configuration or enumeration output.
- [ ] **Host allocation:** Record OS/driver version, allocation API/result, and number of vectors actually granted. Confirm whether the driver requires exactly two or supports the explicitly approved fallback.
- [ ] **Interrupt routing:** Confirm vector 0 CP-completion wiring and vector 1 PTA aggregation. If CP `irq` is not connected to a host ISR yet, mark vector 0 pending rather than passed. Provide simulation or board evidence that CP completion and each PTA cause reach the expected handler.
- [ ] **PTA status behavior:** Verify cause discrimination, `PTA_IRQ_MASK` delivery control, and RW1C clearing for all four PTA causes; attach test name/log or waveform reference.
- [ ] **PTA command queue:** State whether there is a chiplet-local FIFO or one-command-in-flight interface. Record queue depth, whether the active command occupies a slot, behavior during calibration and at capacity, plus the observable status/error. Verify no command is silently dropped.
- [ ] **CP ring capacity and backpressure — proposed lossless contract, not current behavior:** The GPU runtime's CP ring is 64 KiB and its fetcher reads 64-byte cache lines (1,024 lines per ring). Require a host-visible, monotonic 64-bit consumer byte-head with atomic/snapshot read semantics; advance it only after every command in a fetched line has been accepted by the CP engine. Keep the producer tail monotonic in the same byte-offset domain. Compute occupancy as `tail - head` and permit an append only when `occupancy + append_bytes <= 64 KiB`; use the mask only for the physical address. Publish ring contents before the atomic tail doorbell. At full, preserve the command and apply producer backpressure until the head advances; never overwrite unread bytes or silently drop work. Split oversized command batches into capacity-bounded, ordered commits, with the API completion reported only after the final chunk retires; if splitting is not supported, reject the entire batch before publishing any part. Do not wait for space while holding a lock needed by another producer to publish work that lets the CP progress. Source-audit status at GRX-G100 HEAD `f7e7fdaa9979fa1a5594fedae27ab09b26967bb9`: `sw/runtime/common/device.cpp` allocates and programs a host-visible `cp_head_`, but `hw/rtl/cp/VX_cp_fetch.sv` advances `head_r` internally and marks `state_in.head_addr` unused; no AXI writeback to that address is implemented. The runtime append path also does not read a consumer head or enforce free space. This source inspection confirms the approved contract is not implemented; no runtime/RTL modification or passing test is claimed here. Exact-full, wrap, batch-oversize, delayed-acceptance, concurrency and forward-progress tests remain required after the implementation lands.
- [ ] **CP ring full/wrap test cases:** (1) Stall CP consumption, fill exactly to capacity, then attempt more work; confirm no ring bytes, committed tail, or sequence reservation are overwritten, and that the producer resumes with every command exactly once after consumption. (2) Exercise a batch larger than 64 KiB; verify ordered chunking and one final completion, or an up-front rejection with no published prefix. (3) Cross the physical end repeatedly, including the last 64-byte line and the first line after wrap; verify monotonic head/tail, exact command order and sequence count. (4) Delay engine retirement after a line has been fetched; verify storage is reclaimed only after line contents have been accepted and that reuse cannot corrupt the in-flight command. (5) Run concurrent producers at full/near-full occupancy; verify serialized reservations, no lost/duplicate commands, and forward progress. Keep all CP-ring capacities separate from the PTA chiplet-local command-queue depth.
- [ ] **Data-path outstanding window — measurement required:** The existing X2 model assumes 16 lanes at 32 GT/s, 90% payload efficiency (57.6 GB/s per direction), and 100 ns request/return latency; it does not report measured UCIe behavior. Measure useful payload bandwidth separately in each direction and request/response RTT for the selected IP/configuration and representative transfer sizes under unloaded and saturated/concurrent traffic. Record the definition and timestamp endpoints for RTT, payload-byte distribution per transaction, retry/error activity, and the adapter/EIC buffer and credit capacities in bytes and slots. Calculate the initial required window per traffic class/direction as `ceil(measured_payload_bytes_per_second * measured_design_RTT_seconds / measured_payload_bytes_per_transaction)`, then validate against actual credits and buffering under sustained load. If transfer sizes vary, size and report the byte window as well as the slot count. The CP fetcher's 64-byte cache-line read is a measured interface granularity for CP commands only; use it for PTA data only if the selected data path actually transfers that unit. The older 5,760-byte / 90-line / 128-slot illustration is not a measured target and must not be treated as a committed capacity.
- [ ] **X2 evidence disposition:** No measured UCIe payload rate, UCIe transaction-size distribution, end-to-end RTT, or link credit/buffer budget is present in the GRXCP artifacts reviewed. Keep these values open until the GPU/link owner supplies configuration identifiers and reproducible measurement logs; retain the analytical model as a prediction, not silicon or IP evidence.
- [ ] **Completion contract:** State exactly when `PTA_STATUS.BUSY` asserts/deasserts relative to queued, active, and retired commands. Verify the documented predicate: GPU queue empty and one status read shows neither BUSY nor CAL_BUSY.
- [ ] **Disposition:** List unresolved items, owner, and follow-up. Update baseline §8 and the GPU-side interface proposal to match verified behavior; retain open items where evidence is unavailable.

The board-plan figures of 57.6 GB/s and 100 ns are assumptions, and the 64-byte unit is only the current CP command-fetch line size. No UCIe measurements justify a link-window count yet. Do not treat the resulting 5.76 KB or 90-transfer calculation as verified link capacity or queue configuration.
